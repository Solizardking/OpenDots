# ChatGPTEE authentication and deployment

ChatGPTEE at `https://chatgptee.ai` uses a hybrid of Privy and Better Auth under `/api/auth`. Native Solana signatures and verified Privy identities create Better Auth sessions. Google, X and GitHub use the OAuth credentials configured in the existing Privy app. The browser completes Privy's OAuth flow, then the server verifies its access token and user record before creating the application cookie. Social users can open their own workspace without a wallet and explicitly link a Solana wallet later. Signing in does not send a transaction or authorize a payment.

The primary sign-in uses native Sign In With Solana, falling back to an explicit message signature when the wallet does not implement `solana:signIn`. The optional **Sign in with Privy** flow uses the configured Privy app and its Solana Wallet Standard connectors. The server checks the wallet, domain, URI, nonce, timestamps, signature, and browser binding. Each challenge expires after five minutes and can be consumed only once.

The configured PostgreSQL database retains existing users, challenges and legacy sessions in `solana_dots_*`. New Better Auth tables use `chatgptee_auth_*`. Schema initialization is additive and idempotent: existing workspace UUIDs and files remain stable. `better_auth_user_id` maps a verified account to its existing wallet workspace. Social accounts can have no wallet until one is explicitly linked. Wallets are unique; automatic account linking by matching email is disabled. If a social account already has its own workspace, it cannot claim another wallet's existing workspace: sign in with that wallet and link the social provider from **Account** instead. Wallet and social linking require a session created within five minutes.

Better Auth cookies are HttpOnly, SameSite Lax and Secure over HTTPS, with seven-day sessions and server revocation. Existing 24-hour legacy cookies continue to work during migration. A new sign-in revokes and clears the previous legacy cookie; **Sign out** revokes and clears both systems. Simultaneous cookies resolving to different accounts fail closed. Privy tokens are verified server-side for issuer, audience, signature, expiration and matching user ID. When a wallet is supplied, the server additionally verifies linked Solana ownership. Privy tokens are never persisted or returned as application credentials. A cached Privy session does not automatically reopen a logged-out workspace.

Each user gets the existing application backend with its own SQLite file and encrypted OWS vault under `USER_DATA_PATH/<user UUID>/`. Spaces, pages, memories, conversations, Dots, and scheduled jobs remain isolated. Existing schedules resume on startup. Owner Slack mappings and the owner's authenticated browser profile remain in the original owner workspace.

## Account registration

The public sign-in page links **Create an account** to `/register`. `/signup` offers the same registration page; `/login` and `/signin` offer sign-in. The first successful wallet or social sign-in creates the account and private workspace. Returning users open their existing workspace. Registration does not require a token holding, wallet funding, a transaction, or access to the original owner workspace. Native wallet registration preserves Sign In With Solana and the explicit message-signing fallback.

The wallet signature is followed by a server session check before the workspace opens. The private application cookie restores the same account after a reload. Privy exchanges require an actual application account, and expired or future-dated redirect intents are ignored. Registration aliases return to `/` after a successful sign-in. Social account linking still requires its explicit fresh-session flow.

The authenticated account and the connected transaction wallet have separate roles. Connecting, switching, or disconnecting a trading wallet preserves the existing account session and does not relink the account. Each transaction still requires its selected wallet's explicit approval. **Sign out** revokes the account session and disconnects the current wallet.

After deployment, run `node scripts/verify-registration-live.mjs` from this checkout. This uses the normal `https://chatgptee.ai` hostname with no API or provider configuration overrides and no environment file or database credentials. It checks registration aliases, desktop/mobile entry, a fresh native-wallet account, a real Privy wallet callback into the same workspace, reload, cookie protection, logout revocation, and private API denial. It generates a disposable wallet in process memory and disables every transaction signing and broadcast method. Only public identifiers and cookie attributes are written to `artifacts/registration-live`; the empty disposable account remains registered. Provider social buttons are checked, but this wallet verification does not complete a social account login.

Set `REGISTRATION_VERIFY_SOLANA_WORKSPACE=1` for the global Pump.fun and wallet drawer checks using that fresh account. The report distinguishes actual relay launches, provider quotes, account persistence and transaction-context APIs from explicitly marked fixtures for filter controls, unsigned review invalidation and provider-error display. It never approves a transaction.

Each wallet account receives a dedicated Browser Use cloud file workspace when it first starts a task. Its namespace is persisted locally and reused across that account's Dots, sessions, and restarts. Older sessions in the shared namespace require a new task before continuing. Public-account MCP connections support public HTTP(S) endpoints: DNS results are checked and pinned for each request, and private network addresses and redirects are rejected. The existing owner workspace retains its original connection configuration.

The original database at `DATABASE_PATH` remains accessible through **Existing workspace owner** using `OWNER_TOKEN`. Wallet registration never grants access to that workspace. Keep the original owner ID, database path, and computer namespace stable.

## Server configuration

Configure `DATABASE_URL`, `PRIVY_APP_ID`, `PRIVY_CLIENT_ID`, `PRIVY_APP_SECRET`, `PRIVY_AUTH_ORIGIN`, and a random owner token in the ignored `.env` or hosting environment. No secret belongs in a `VITE_` variable. The browser receives only the public Privy app ID and client ID. The supplied wallet authorization key is not required for login and is not used to sign transactions or enable automatic approvals.

## Supabase database

Supabase PostgreSQL backs the existing Privy/Better Auth sign-in without changing its provider or session cookies. Set `DATABASE_URL` to the supplied session-pooler connection on port 5432. If it is absent, the server accepts `POSTGRES_URL_NON_POOLING`, then `POSTGRES_URL`, then `POSTGRES_PRISMA_URL`. These values remain server-only. The runtime includes Supabase's official CA and verifies both the certificate chain and hostname; an explicit `sslrootcert` path is also supported.

Startup creates or migrates the three `solana_dots_*` identity/challenge/session tables and five `chatgptee_auth_*` tables. Row-level security is enabled, and public, `anon`, and `authenticated` table grants are revoked for those eight backend-only tables. The owning PostgreSQL role retains backend access. Other tables and Storage buckets are unaffected.

| Data                                                                             | Persistence                            |
| -------------------------------------------------------------------------------- | -------------------------------------- |
| User profiles, linked identities, sign-in challenges, sessions, auth rate limits | Supabase PostgreSQL                    |
| Dots, chats, pages, schedules, preferences, memory outbox/cache                  | Per-user SQLite under `USER_DATA_PATH` |
| Extracted long-term memories                                                     | Mem0, when permitted and configured    |
| Wallet secrets                                                                   | Encrypted per-user OWS vault           |

Supabase's native Auth and Storage APIs can be reachable without being used by this app. The existing browser continues to call same-origin authentication APIs; workspace files are not automatically uploaded to Supabase Storage. The supplied `NEXT_PUBLIC_*` aliases are accepted by the diagnostic script but are not exposed by this Vite app. Keep privileged Supabase keys server-side.

Run `node --env-file=.env --import tsx scripts/verify-supabase.ts` to check the real database, generated-wallet sign-in, session persistence after a server restart, logout, and public API denial for all eight tables. It starts a temporary local web runtime, removes its fixture identity, and writes `artifacts/supabase-verification/verification.json`. Run `python3 scripts/check-hybrid-auth.py` for disposable local PostgreSQL tests; never point `HYBRID_TEST_POSTGRES_URL` at a shared cloud project.

References: [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres), [verified PostgreSQL TLS](https://supabase.com/docs/guides/platform/ssl-enforcement), [row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Hosting

The dedicated Railway project is `596f393d-8079-461b-8260-8271ecc54921`, production environment `ad905a53-be25-44f7-8b26-1fa311e4548a`, service `3340e3ae-457e-4006-b6bd-5affc4bb2ec6`. Build with `deployment/Dockerfile.chatgptee`. The entrypoint initializes the mounted volume, then drops to the non-root Node user; `/healthz` checks database readiness. Its `/data` volume preserves workspace databases and encrypted vaults across deployments. Keep one replica because the existing workspace backend uses SQLite and an in-process scheduler. The hosted service uses its configured PostgreSQL user/session database. Switching a hosted instance to Supabase requires preserving its existing auth records as well as the mounted workspace volume.

The Cloudflare Worker in `deployment/chatgptee-edge.mjs` owns `chatgptee.ai` and redirects `www.chatgptee.ai` to the apex. It forwards HTTP requests, cookies, and streaming responses to the Railway app. It does not hold database or provider credentials. Responses use `no-transform` so Cloudflare preserves the payload and does not inject an additional analytics beacon; see [Cloudflare automatic beacon injection](https://developers.cloudflare.com/web-analytics/get-started/). Deploy its config from the parent checkout with:

```sh
npx wrangler deploy --config OpenDots/deployment/wrangler.chatgptee.jsonc --keep-vars
```

Verify the normal hostname, wallet callback, protected API response, session restoration, and logout after each deployment. A built image or a loaded sign-in button alone does not prove authentication.

## Better Auth joins and trusted client IPs

Better Auth 1.7.7 uses the existing native PostgreSQL pool with `advanced.database.joins: true`; the UUID generator and cookie settings remain in place. The PostgreSQL/Kysely adapter supports native joins, so this deployment does not need generated Drizzle relations or Prisma migrations. Joined session reads are verified against disposable PostgreSQL, including the existing foreign keys, identity mapping, logout, and private table policies. Measure uncached session requests before claiming a production speedup: the documented 2–3x improvement depends on database latency and request shape.

Production requires a random `CHATGPTEE_PROXY_SECRET` of at least 32 characters, stored with the same value in Cloudflare Worker secrets and Railway service variables. Send it through stdin when using deployment CLIs; never add it to Wrangler vars, frontend configuration, logs, or tracked files. Deploy the Worker and backend as one coordinated change. Keep `/healthz` available for Railway.

The Worker overwrites `x-chatgptee-client-ip` from Cloudflare's `cf-connecting-ip`, overwrites `x-chatgptee-proxy-secret` with its private origin credential, and removes caller-supplied forwarding headers. All `/api/auth/*` routes—including aliases, legacy sign-in routes, and OAuth callbacks—require the verified origin credential and one valid IP before handlers run. Direct Railway auth requests return 403. Better Auth receives only the sanitized IP header; the origin credential is removed before its handlers and dashboard plugin receive headers. In local mode, the socket peer supplies the IP; arbitrary forwarding headers remain ignored.

Better Auth trusts only `x-chatgptee-client-ip`, with IPv6 `/64` normalization and its existing database-backed limits: 60 requests/minute generally and 10/minute for Solana nonce/verify, Privy bridge, and social sign-in. There is no generic X-Forwarded-For fallback and no broad trusted proxy CIDR. IP limits are shared by users behind the same NAT or IPv6 subnet; monitor false positives before tuning them. Keep token, cookie, signature, CSRF, origin, and account-linking checks independent of IP rate limiting.

Validation uses `python3 scripts/check-hybrid-auth.py` for disposable PostgreSQL and `npm test -- --run tests/auth-proxy.test.ts tests/chatgptee-edge.test.mjs` for the boundary. Tests verify independent IP counters, forwarding-header spoof resistance, origin rejection, IPv6 subnet limits, a single joined session/user query, and `429` with Better Auth's `X-Retry-After` header. In production, verify canonical sign-in/session/logout, direct-origin rejection, and unchanged health before calling the rollout complete. Do not run schema generation or destructive test resets against production.

References: [Better Auth rate limiting](https://better-auth.com/docs/concepts/rate-limit), [PostgreSQL joins](https://better-auth.com/docs/adapters/postgresql#joins), and [configuration options](https://better-auth.com/docs/reference/options).

## Privy agent access

Production device approval is hosted at `https://chatgptee.ai/authorize` for the existing ChatGPTee app. `PRIVY_AUTH_URL` is the approval page, while `PRIVY_AUTH_ORIGIN=https://privy.chatgptee.ai` is the Privy SDK custom authentication origin. `PRIVY_SIGNING_KEY` is a server-only P-256 authorization key. It is never a browser variable or an agent credential. The device flow obtains its own expiring user authorization key through HPKE.

Users sign in through Privy, match their agent code, and explicitly approve or deny. The portal creates a user-owned agent wallet only on request. The owner is the verified Privy subject, and a deterministic external wallet ID makes repeated creation requests reuse the same wallet. These Wallet API wallets support headless agent signing; browser-created on-device payment wallets may not. The same page lists active grants and lets users revoke them. Revocation blocks token refresh immediately; issued access tokens can remain valid for up to 15 minutes. Embedded payment wallets are created only when the user chooses a wallet creation button. External wallets used for sign-in do not give a headless agent their signing keys.

Install the downloadable CLI from `https://chatgptee.ai/agent/chatgptee-agent-0.1.1.tgz`. Its source is in `agent/`, with its own dependency lockfile because the official server SDK uses Solana Kit 5 while the web application uses Kit 7. It uses the OS credential manager without a plaintext fallback. Linux requires a working Secret Service keyring. Never give the CLI an app secret or server signing key.

The browser payment panel uses Privy `useX402Fetch` for x402 v1, with a reviewed recipient, asset, network and amount and a maximum of 1 USDC. Requests proxy only to the listed CoinGecko and Allium origins and never forward Privy bearer tokens, cookies, or server keys to providers. x402 v2 payments use the CLI's current `@x402/fetch` and Privy-backed signers. The CLI checks USDC, network and a positive per-request limit of at most 1 USDC before requesting a signature. These per-request checks are separate from wallet policies governing an entire authorization. Fund the selected embedded wallet with USDC on the API network before making a payment.

`public/agent/SKILL.md` documents installation, approval, RPC, payments and revocation. `scripts/verify-agent-access.ts` verifies the production device flow with a generated test identity and a message signature without making a transaction or payment.
